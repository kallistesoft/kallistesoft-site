CI/CD pour une petite équipe de développement

Par Kallistesoft · 28 novembre 2026 · Lecture : 3 min

Dans une grande entreprise, la livraison continue est portée par une équipe de plateforme. Dans une équipe de deux à dix personnes, c'est vous qui la mettez en place. Ce qui fonctionne : peu de règles, bien appliquées, et une automatisation qui grandit avec l'équipe.

Branches et demandes de fusion

Une branche principale toujours déployable, des branches courtes, et des règles minimales (protection de branche) :

  • Aucun commit direct sur main : tout passe par une demande de fusion.
  • Au moins une revue. Seul? Relisez votre demande le lendemain.
  • Des demandes lisibles en quinze minutes : une demande de 2000 lignes n'est pas relue, elle est approuvée.
  • Fusion permise seulement si les vérifications automatiques passent.

Un pipeline minimal

Le premier pipeline fait peu, mais à chaque demande : installer, vérifier le style, tester, construire (GitHub Actions).

name: CI
on:
  pull_request:
  push:
    branches: [main]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: npm }
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build

Utilisez npm ci pour des installations reproductibles, mettez les dépendances en cache et visez moins de dix minutes : au-delà, les gens contournent le pipeline. Côté barrières, un linter et un formateur, puis des tests sur ce qui coûte cher quand ça casse (calculs, paiements, migrations). Inutile de viser 100 % de couverture. Un test instable se corrige ou se retire vite; relancer « jusqu'à ce que ça passe » ruine la confiance.

Déployer à la fusion

Une fois la base stable, déployez quand main change. Ce site fonctionne ainsi : une fusion déclenche une action qui téléverse les fichiers par FTPS. Rien de sophistiqué, mais c'est reproductible.

  deploy:
    needs: verify
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/deploy.sh
        env:
          FTP_PASSWORD: ${{ secrets.FTP_PASSWORD }}

Le mot-clé environment permet d'exiger une approbation manuelle (documentation).

Secrets et retours en arrière

  • Jamais de mot de passe ou de clé dans le dépôt, même privé : l'historique Git est permanent. Utilisez les secrets GitHub, aux droits minimaux (compte FTP limité au dossier du site).
  • Fuite? Révoquez d'abord, nettoyez ensuite.
  • Retour arrière : redéployez un commit précédent ou annulez (revert) la fusion. Séparez les migrations de base de données du code; supprimer une colonne ne se défait pas. Essayez-le une fois à froid.

Mobile : build et signature

Automatisez tôt la compilation, les tests, le numéro de build et la distribution de builds de test (Firebase App Distribution, TestFlight, pistes de test de Google Play). La signature demande de la rigueur (documentation Android) : clés hors du dépôt, encodées dans les secrets et sauvegardées ailleurs, car perdre une clé peut bloquer vos mises à jour.

Pas encore

Gardez un geste humain pour la publication finale dans les magasins, évitez les tests de bout en bout exhaustifs (lents et fragiles) et résistez à Kubernetes pour une application qui tient sur un serveur.

Plan en quatre semaines

  1. Semaine 1 : protection de main, revue obligatoire, linter.
  2. Semaine 2 : CI minimal comme barrière de fusion.
  3. Semaine 3 : secrets dans GitHub, déploiement automatique en test.
  4. Semaine 4 : production à la fusion, retour arrière exercé.

Conclusion

Une CI/CD de petite équipe doit être fiable et comprise de tous, pas impressionnante. Ajoutez le reste quand un vrai problème le justifie.
