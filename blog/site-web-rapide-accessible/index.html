Créer un site web rapide et accessible

Par Kallistesoft · 28 novembre 2026 · Lecture : 3 min

Un site rapide et accessible relève surtout de bons choix au départ. Après dix ans à livrer des sites et des applications, dont ce site-ci en HTML statique, je vois toujours les mêmes erreurs : trop de JavaScript, des images énormes, des contrastes faibles, un clavier oublié.

HTML statique ou framework ?

Pour un site vitrine ou un blogue, le HTML statique est difficile à battre : le navigateur reçoit une page finie, sans attendre qu'un script la construise. Notre site se déploie par GitHub Actions sur un hébergement ordinaire, avec presque rien à entretenir. Un framework se justifie quand l'état de l'interface est complexe (tableaux de bord, formulaires dynamiques). Même alors, générez le contenu à l'avance et réservez le JavaScript aux zones interactives.

Les Core Web Vitals

Google publie des seuils « bons » pour trois indicateurs (web.dev) :

IndicateurMesureSeuilLevier principal
LCPAffichage du plus gros élément2,5 sServir l'image principale tôt, CSS léger
INPRéactivité aux interactions200 msMoins de JavaScript, pas de widgets tiers inutiles
CLSDécalages de mise en page0,1Dimensions d'images déclarées, espace réservé

Pour le LCP, pas de loading="lazy" sur l'image principale. Pour le CLS, déclarez toujours les dimensions :

<img src="/img/atelier-800.webp" width="800" height="450"
     alt="Poste de travail avec deux écrans">

Images, polices et cache

  • Images : WebP ou AVIF pour les photos, SVG pour logos et icônes. Jamais 4000 px dans un espace de 400 px : utilisez srcset.
  • Polices : une seule famille, font-display: swap, ou simplement une pile de polices système, la plus rapide.
  • Cache : les fichiers versionnés (style.css?v=20261108) se cachent longtemps, le HTML se revalide (MDN). Activez la compression gzip ou Brotli.
Cache-Control: public, max-age=31536000, immutable   # fichiers versionnés
Cache-Control: no-cache                              # pages HTML

Accessibilité de base

Utilisez un HTML sémantique : header, nav, main, une seule h1, des titres dans l'ordre, <button> pour les boutons et <a href> pour les liens. Un <div onclick> n'est ni focalisable ni annoncé par un lecteur d'écran. Déclarez lang et étiquetez chaque champ.

Les WCAG demandent un contraste d'au moins 4,5:1 pour le texte normal (critère 1.4.3). Le gris pâle sur blanc est le fautif habituel; vérifiez les deux thèmes si vous offrez un mode sombre. Le texte alternatif décrit la fonction de l'image en une phrase; une image décorative reçoit alt="". Au clavier, ne supprimez jamais le focus sans le remplacer :

:focus-visible { outline: 3px solid #2f6bff; outline-offset: 2px; }

Comment tester

  • Lighthouse (outils de Chrome), en mode mobile : fiez-vous aux tendances, pas à un score isolé.
  • axe : détecte contrastes, étiquettes manquantes, ARIA invalide, mais seulement une partie des problèmes.
  • Clavier seul : Tab, Maj+Tab, Entrée, Espace. Pouvez-vous tout faire en voyant où vous êtes?
  • Lecteur d'écran : dix minutes avec VoiceOver ou TalkBack sur vos pages clés.

Liste de vérification

  • Une h1, lang déclaré, titres dans l'ordre.
  • Images modernes, avec dimensions et alt.
  • Cache long sur les fichiers versionnés, compression active.
  • Contraste 4,5:1, focus visible, tout utilisable au clavier.

Conclusion

Performance et accessibilité s'obtiennent avec les mêmes réflexes : moins de code, du HTML correct, des images raisonnables. Appliquez la liste à votre page la plus visitée, mesurez, puis recommencez.
